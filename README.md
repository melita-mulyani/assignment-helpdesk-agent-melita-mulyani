# IT Helpdesk Assistant — End-to-End RAG & AI Agent

## 1. Project Overview

IT Helpdesk Assistant is an internal helpdesk application that helps employees obtain IT-related information and check the status of their support tickets.

The application combines Retrieval-Augmented Generation (RAG), intent routing, tool integration, and a FastAPI endpoint.

### Objectives

- Answer employee questions using an internal IT Helpdesk knowledge base.
- Retrieve relevant FAQ entries using semantic search.
- Generate answers based on retrieved FAQ context using Gemini.
- Check support ticket status using mock ticket data.
- Expose the application through a REST API.
- Package and run the application using Docker.

## 2. Architecture

The application follows this flow:

1. The employee submits a query through the `/ask` API endpoint.
2. FastAPI receives the request.
3. The intent router determines whether the query is an FAQ question, a ticket status request, or an unknown request.
4. For FAQ questions, the RAG module retrieves relevant documents using embeddings and FAISS, then generates an answer using Gemini.
5. For ticket status requests, the ticket tool searches the mock ticket dataset.
6. The API returns a structured response to the user.

### Main Components

| Component | Responsibility |
|---|---|
| `main.py` | Defines the FastAPI endpoints and request/response models. |
| `router.py` | Detects intent and routes requests to the appropriate component. |
| `rag.py` | Generates embeddings, builds a FAISS index, retrieves relevant FAQ entries, and generates answers using Gemini. |
| `tools.py` | Retrieves ticket information from the mock ticket dataset. |
| FAISS | Performs similarity search over FAQ embeddings. |
| Gemini API | Provides text embeddings and generates FAQ responses. |

## 5. Configuration

### Prerequisites

- Python 3.12 for local execution.
- Docker Desktop for container execution.
- A valid Gemini API key.

### Environment Variables

Create a `.env` file in the project root directory:

```text
GEMINI_API_KEY=your_actual_api_key_here
```

Replace the placeholder with your own API key.

The `.env` file contains a secret and must not be committed to GitHub. The `.env.example` file should contain only a placeholder:

```text
GEMINI_API_KEY=your_api_key_here
```

## 6. Running Locally

Open PowerShell in the project directory.

### Step 1: Create and activate a virtual environment

```powershell
py -3.12 -m venv .venv
.\.venv\Scripts\Activate.ps1
```

### Step 2: Install dependencies

```powershell
python -m pip install -r requirements.txt
```

### Step 3: Configure the API key

Create the `.env` file and configure `GEMINI_API_KEY` as described in Section 5.

### Step 4: Start the application

```powershell
python -m uvicorn app.main:app --reload
```

The application will be available at:

- Health check: `http://127.0.0.1:8000/health`
- API documentation: `http://127.0.0.1:8000/docs`

## 7. Running with Docker

Ensure Docker Desktop is running and the `.env` file contains a valid Gemini API key.

### Step 1: Build the Docker image

```powershell
docker build -t it-helpdesk-assistant .
```

### Step 2: Run the container

```powershell
docker run --name it-helpdesk-container -p 8000:8000 --env-file .env it-helpdesk-assistant
```

The application will be available at `http://127.0.0.1:8000`.

### Step 3: Stop the container

Press `Ctrl + C` in the terminal running the container.

To start the existing container again:

```powershell
docker start -ai it-helpdesk-container
```

## 8. API Endpoints

### Health Check

**Endpoint:** `GET /health`

Example response:

```json
{
  "status": "ok"
}
```

### Ask the Helpdesk Assistant

**Endpoint:** `POST /ask`

Request body:

```json
{
  "query": "Bagaimana cara mengajukan cuti?"
}
```

Example response:

```json
{
  "status": "success",
  "intent": "faq",
  "data": "Jawaban berdasarkan informasi FAQ yang relevan."
}
```

The actual answer is generated by Gemini and may differ in wording.

## 9. Testing

The following scenarios are used to evaluate the application.

| Test scenario | Example query | Expected behavior |
|---|---|---|
| FAQ retrieval | `Bagaimana cara mengajukan cuti?` | Returns a knowledge-based answer. |
| FAQ paraphrase | `Bagaimana prosedur pengajuan cuti?` | Retrieves relevant FAQ information. |
| Existing ticket | `Cek status tiket TICKET-0001` | Returns ticket details and status. |
| Unknown ticket | `Cek status tiket TICKET-9999` | Returns a ticket-not-found response. |
| Out-of-scope query | `Berapa harga tiket konser Taylor Swift?` | Returns an unknown-intent response. |

### Observed Test Results

The following results were confirmed during testing:

- The `/health` endpoint returned `{"status":"ok"}`.
- The FAQ request returned a successful response with intent `faq`.
- The `TICKET-0001` request returned a successful response with intent `ticket_status`.
- The ticket record showed status `Selesai`.
- Both FAQ and ticket status requests returned HTTP `200 OK` when tested in Docker.

The remaining scenarios should be rerun in Docker if complete container-level test evidence is required.

## 10. RAG Evaluation

The knowledge base contains 31 FAQ entries.

The FAISS index was successfully created with 31 FAQ vectors. A test query about leave application retrieved the following relevant entries:

1. **How to apply for leave?** — similarity score approximately 0.8167.
2. **Can emergency leave be requested at short notice?** — approximately 0.7744.
3. **How to check remaining leave balance?** — approximately 0.7481.

These results demonstrate that the embedding and retrieval pipeline can identify FAQ entries related to the user's query.

The generated response also preserved the key information in the retrieved FAQ about the minimum application lead time and supervisor approval.

Similarity scores are specific to the embedding and retrieval configuration used in this experiment.

## 11. Limitations

- Ticket information is retrieved from a mock CSV dataset rather than a live ticketing system.
- FAQ answers depend on the coverage and accuracy of the knowledge base.
- Intent detection uses keyword-based routing and may not correctly classify every possible query.
- Gemini API access and availability are required for embedding and answer generation.
- The FAISS index is built in memory and is recreated when a new application process starts.

## 12. Conclusion

The project demonstrates an end-to-end IT Helpdesk Assistant that integrates semantic retrieval, LLM-based answer generation, intent routing, tool integration, and a REST API.

The application was tested locally and in Docker, including FAQ retrieval and ticket status lookup. It provides a foundation for further improvements, such as more robust intent classification, automated testing, and integration with a real ticket management system.
